# A3 — Identifier catalogue and stable-child-ID workflow audit

READ-ONLY. No file in `D:\parentcontrol_app` was modified by this audit.
Evidence is `file:line`. Scope: Supabase migrations, Edge Functions, Kotlin/Dart client.

## PART 1 — Identifier catalogue

### 1. Supabase auth uid / `profiles.id` (parent and child)
- Identifies: one human account (parent or child). The only identity that owns memberships.
- Generated: Supabase GoTrue (server) at signup; client trigger is
  `lib/data/repositories/supabase_auth_repository.dart:70-74` (`auth.signUp(email, password,
  data:{display_name})`). Row mirrored into `public.profiles` by trigger
  `private.handle_new_user` `supabase/migrations/20260101000000_core.sql:456-486`.
- Format/entropy: UUID v4 (122 bits), 36-char text. PK + FK to `auth.users`
  `core.sql:17-25`; immutability enforced by trigger `core.sql:491-499`
  (`profile id is immutable`).
- Stable: YES — across reboot, reinstall, sign-out, device loss. Re-obtained by email+password.
- Secret/public: semi-private. Not a credential, not displayed anywhere in the UI; RLS lets a
  caller read only self or same-active-family profiles
  `supabase/migrations/20260101000200_rls.sql:27-31`.
- Stored: `auth.users`, `public.profiles.id`; client-side in the persisted GoTrue session and
  `lib/data/services/session_service.dart:16,34` (`userId`).
- Authenticated on use: Bearer JWT re-verified server-side with `db.auth.getUser(token)`
  `supabase/functions/_shared/auth.ts:80-127`, then role re-check `auth.ts:129-139`; RLS uses
  `auth.uid()`. Email must be confirmed for pairing/register
  (`auth.ts:118-125`, used at `supabase/functions/pairing/index.ts:200`).
- Role: set once via `supabase/functions/auth-bootstrap/index.ts:32-64` (`set_role`), immutable
  afterwards except service role (`core.sql:500-508`).

### 2. Family id + `family_members` rows and roles
- `families.id`: UUID `gen_random_uuid()` `core.sql:34`; created server-side only, inside
  `private.create_family_with_owner` `supabase/migrations/20260101000100_functions.sql:44-81`,
  called by `auth-bootstrap` action `create_family` (`index.ts:67`). One active family per owner
  (`core.sql:48-50`). Stable while the row exists; soft-deletable (`deleted_at`).
  Readable by active members only `rls.sql:43-47`; `owner_id` immutable to clients (`core.sql:519-538`).
- `family_members.id`: UUID `core.sql:56`. Written ONLY by service-role code paths:
  parent row `functions.sql:67-68`, child row on child approval `functions.sql:272-274`,
  removal `functions.sql:375-377`. Client has SELECT-only grant `rls.sql:255-256`.
  `role in ('parent','child')` `core.sql:59`; `status in ('active','removed')` with
  removed-consistency check `core.sql:60,64-65`; `(family_id,user_id)` unique `core.sql:63`;
  a child can hold only ONE active child membership `core.sql:69-71`.
- Not secret; not an authorization token — every use is re-asserted with `assertFamilyParent` /
  `assertChildMembership` (`auth.ts:194-222`).

### 3. `devices.id`, installation id, `device_id` header, device credential
- `devices.id`: UUID `core.sql:80`; generated by the DB on INSERT performed by
  `supabase/functions/device-register/index.ts:182-184` (re-register) and `:214-223` (new row).
  Returned to the child app and stored client-side:
  `lib/features/child/controllers/child_enrollment_controller.dart:258-262` →
  `DeviceIdentity.serverDeviceId` `lib/data/models/device.dart:720,729` and, for background
  sync, `android/.../SecureStore.kt:32,106-114` (`sync_device_id`).
  Stable only as long as the row survives; it is *not* the same object as an installation.
  Public within the family (`devices_select_parent_or_child` `rls.sql:68-72`). Not a credential:
  `requireActiveDeviceForParent` still needs a verified parent JWT `auth.ts:253-275`.
- `installation_id`: generated CLIENT-side — `UUID.randomUUID()` first call, then persisted
  `android/.../SecureStore.kt:85-91` in `EncryptedSharedPreferences`
  (`SecureStore.kt:70-83`), surfaced through `NativeBridge.kt:150-164`
  (`device_admin_service.dart:35-51`). Format: 36-char UUID; validated 8..128 + charset
  `supabase/functions/_shared/validation.ts:10,216-226`, column check `core.sql:83-84`.
  Identifies an *app install*, not a phone or a person.
  Stable across reboots; NOT stable across uninstall or "clear data" — `allowBackup="false"`
  `android/app/src/main/AndroidManifest.xml:40`, and the file is app-private storage.
  Server-side it is `(family_id, installation_id)` unique `core.sql:111` and is a SERVICE-ONLY
  column: excluded from the authenticated column grant `rls.sql:257-266`, stripped from
  responses `device-register/index.ts:44-49` and `functions.sql:463,503`.
- `x-device-id` header: the `devices.id` UUID
  (`device.dart:729-735`; native sender `DeviceHttpClient.kt:45`; contract
  `docs/api-contract.md:110-115`). Never sufficient alone — `auth.ts:281-300` requires both
  headers, and a user JWT is never accepted as device proof (`docs/api-contract.md:114-115,283-290`).
- `x-device-secret` (device credential): 32 bytes from `java.security.SecureRandom`,
  base64url no-wrap/no-padding (~43 chars, 256 bits) `SecureStore.kt:93-104`.
  Secret; transmitted over TLS to Edge Functions (`DeviceHttpClient.kt:46`); stored only in
  EncryptedSharedPreferences (`sync_device_secret` `SecureStore.kt:33,111`).
- `secret_hash`: SHA-256 hex computed ON THE PHONE (`SecureStore.kt:59-67`,
  `NativeBridge.kt:156-161`), sent at register (`supabase_device_repository.dart:87`) and
  validated as 64-hex (`device-register/index.ts:123`, `core.sql:93-94`). Server verifies by
  hashing the header and constant-time comparing (`auth.ts:312-328`), then requires
  `status='active'` and `credential_revoked_at is null` (`auth.ts:329-335`). Rotated on every
  re-register (`device-register/index.ts:155-164`); nulled on unlink/revoke
  (`functions.sql:379-385`, `467-471`).

### 4. 8-character pairing code + `device_pairing_tokens.id` + `code_hash`
- Code: generated SERVER-side in the child's `pairing.create` call
  `supabase/functions/pairing/index.ts:221` by `generatePairingCode()`
  `validation.ts:237-251` (rejection-sampled over a 30-char alphabet
  `validation.ts:12-14`, 8 chars ⇒ ~30^8 ≈ 39.5 bits, uniform).
- TTL 10 minutes (`pairing/index.ts:36,223-225`); creating a new token revokes all other active
  tokens for that child (`:248-254`) and cancels pending requests (`:256-261`); max 5 creations
  per 24 h (`_shared/rate_limit.ts:8,70-88`).
- Secret: the plaintext exists only inside the HTTP response to the child
  (`pairing/index.ts:270-274`, plus `qr_payload = parentcontrol://pair?code=<code>&v=1`) and in
  the child UI (`lib/features/child/child_enrollment_page.dart:226-276`, including a Copy button).
  Never stored: `code_hash = SHA-256(normalized code)` (`pairing/index.ts:222`, normalized at
  `:284` via `normalizePairingCode` `validation.ts:228-230`), UNIQUE column
  `core.sql:131-132`.
- `device_pairing_tokens.id`: UUID `core.sql:129`, produced by the INSERT at
  `pairing/index.ts:227-237`. Internal only — table has no RLS policies and no grants
  (`rls.sql:9,74,286-288`), and it is echoed back to the parent as `token_id`
  (`pairing/index.ts:133-151`). It identifies a *code instance*, not a child or a device; the
  token has no `device_id` column at all (`core.sql:128-142`).
- Single-use: `pairing_requests.token_id` is `UNIQUE` `core.sql:154-155`; approve ⇒ `redeemed`
  `functions.sql:280-282`; reject/cancel ⇒ `revoked` `functions.sql:301-303`,
  `pairing/index.ts:521-525`.

### 5. `pairing_requests.id`
- UUID `core.sql:153`, created by the parent's redeem INSERT
  `pairing/index.ts:375-386`; `status pending_child|approved|rejected|cancelled|expired`
  `core.sql:159-160`, `expires_at` copied from the token `:383`.
- Visible to the child, the requesting parent, and any family parent
  (`rls.sql:79-87`); SELECT-only grant `rls.sql:267`; no client write path.
- Used as `request_id`: approve/reject requires `p_child_user_id = auth.uid()` matching the row
  (`pairing/index.ts:462-477` → `functions.sql:215-217`), cancel requires family parent
  (`pairing/index.ts:489-494`).

### 6. Remote session ids and signal rows
- `remote_sessions.id`: UUID `core.sql:322`, inserted by `remote-session` action `request`

  (parent JWT + active device + active family-parent membership, `auth.ts:253-275`).
- `session_nonce`: UUID generated at start — `remote-session/index.ts:189`
  (`crypto.randomUUID()`), column `core.sql:343`; internal, not a credential users exchange.
- `webrtc_signals.id` UUID `core.sql:359` plus `sequence bigint generated always as identity`
  `core.sql:366-367`; `from_user_id` DEFAULTS to `auth.uid()` `core.sql:361` and clients insert
  rows directly via PostgREST (`supabase_remote_session_repository.dart:181-190`) gated by
  `rls.sql:202-231` (live session, participant, self-authored). Realtime topics are
  `kind:uuid` and gated by `private.realtime_topic_allowed` `rls.sql:295-332`.
- `device_commands.idempotency_key`: client-generated UUID v4
  (`app_restrictions_controller.dart:396`, `screen_time_controller.dart:345`), 1..128 chars,

### 7. Audit log target ids
- `audit_logs.target_type text` / `target_id text(≤128)` `core.sql:381-382`. `target_id` is the
  stringified UUID of the referenced row — free text, no FK.
- Observed `target_type` values: `family`, `profile`, `device`, `device_policy`,
  `device_command`, `device_pairing_token`, `pairing_request`, `remote_session`, `safety_alert`,
  `family_member` (e.g. `functions.sql:72` family id, `:290`/`:311` pairing request id,
  `:414` membership id, `:497` device id; `pairing/index.ts:266-267` token id;
  `auth-bootstrap/index.ts:59-61` target = `auth.user.id`).
- Append-only to clients (`core.sql:543-565`), readable only by family parents
  (`rls.sql:236-240`) — so any new identifier written into `target_id` becomes parent-visible.

### Interchangeability — disproved, not assumed
- Code ≠ device id ≠ uid: the redeem path accepts only `{code, family_id}`
  (`pairing/index.ts:280-281`); it resolves code→token→`child_user_id` (`:293-301`) and never
  touches `devices`. Conversely a `devices.id` cannot authorize a user action
  (`auth.ts:277-280` comment plus the `requireDevice`/`requireUser` split), and an
  `installation_id` cannot authorize anything — it is an upsert key scoped by
  `family_id` (`core.sql:111`, `device-register/index.ts:143-176`).
- Identity for pairing always comes from the JWT (`pairing/index.ts:200-201`, `:429-430`,
  `:463-464`); device identity always from the two headers (`auth.ts:281-337`).
- The child's `devices.child_user_id` is taken from the JWT, never from the request body
  (`device-register/index.ts:218`), so presenting an id is not the same as proving it.

## PART 3 — Is there already a stable shareable child ID?

**Yes — the auth uid / `profiles.id`** (§1). It is server-assigned, immutable, child-scoped, and
the schema already constrains exactly the cardinality the product wants: one active family per
child (`core.sql:69-71`) and one active device per child (`core.sql:117-119`).
Neither `devices.id`, `installation_id`, the pairing code nor `device_pairing_tokens.id` can
substitute: the first two are installation-scoped and die with an uninstall
(`SecureStore.kt:85-104` + `AndroidManifest.xml:40`), the last two are rotating 10-minute secrets
(`pairing/index.ts:36,248-254`) that name a *code*, not a child.

What stops "enter it once, child approves":

1. **Structural blocker:** `pairing_requests.token_id uuid NOT NULL UNIQUE`
   `core.sql:154-155`. A request cannot exist without a redeemed code token, so there is no
   invite-without-code row to approve.
2. **No lookup/invite RPC:** nothing in `20260101000100_functions.sql` or any
   `supabase/functions/*/index.ts` takes a child uid and produces a request; `redeem` accepts only
   `{code, family_id}` `pairing/index.ts:280-281`.
3. **No parent UI for it:** "Link a child" is code field + QR scanner only
   (`pairing_redeem_page.dart:43-63`).
4. **No child UI for it:** the app never renders the account uid; `SessionService.userId`
   (`session_service.dart:16,34`) is used only for equality checks
   (`child_shell_controller.dart:819`, `family_controller.dart:43-45`,
   `audit_logs_controller.dart:43`). There is no "your ID / QR of your ID" surface.
5. **Anti-enumeration by design:** RLS forbids reading a stranger's profile
   (`rls.sql:27-31`), and the contract states "Do not expose any directory search"
   (`docs/api-contract.md:312-313`), so a uid-only path needs an explicit, rate-limited RPC —
   today's limits are keyed on `parent_user_id` and `code_hash` only
   (`rate_limit.ts:14-47`).

## Abuse surface if a stable ID became sufficient for linking (guards today)

- **Identity confusion / handle reuse:** the code's ~39.5-bit entropy + 10-min TTL + single use
  (`validation.ts:12-14`, `pairing/index.ts:36`, `core.sql:154`) are what currently make a link
  attempt unguessable and non-replayable. A permanent, human-typeable child ID replaces all three;
  the only remaining guard would be the child's approval (`functions.sql:215-217`) and the
  "child not already linked" checks (`core.sql:69-71`, `functions.sql:249-257`).
- **Enumeration:** today unknown and expired codes return the *same* `invalid_code`
  (`pairing/index.ts:301-318`, contract `docs/api-contract.md:309-311`) and 5 attempts/parent/10 min
  + 10/code (`rate_limit.ts:5-7`). A uid-based path has no equivalent counter — `pairing_attempts`
  is keyed by `code_hash` (`core.sql:417`), so it cannot rate-limit "guess child IDs".
- **Approval fatigue / spam-to-child:** the child list is capped at 50 rows per call
  (`pairing/index.ts:455`) but there is **no per-parent pending-request quota**. With a public
  stable ID, any parent could queue requests for a child to review; today that is impossible
  without the child first minting a code.
- **Weak verification display:** the child identifies the requester only from
  `family_name` + `parent_display_name` (`pairing/index.ts:100-117`), and `display_name` is a
  self-chosen 1..60-char string (`core.sql:21-22`; updatable by the user — grant
  `rls.sql:251`). This is the sole impersonation check the approval UI rests on
  (`child_enrollment_page.dart:284-296`).
- **Identifier leakage:** `devices.secret_hash` and `installation_id` are deliberately stripped
  (`rls.sql:257-266`; `device-register/index.ts:44-49`; `functions.sql:463,503`). Any new ID
  surface must not widen those grants, and `audit_logs.target_id` is free text readable by every
  family parent (`core.sql:382`, `rls.sql:236-240`) — writing a shareable ID there makes it
  parent-visible.
- **Id-not-proof:** `device-register` ignores a body-supplied child identity and uses the JWT
  (`device-register/index.ts:118-141,218`), and no header-based device id is trusted without the
  secret (`auth.ts:281-337`). Those two patterns are the existing guard against a stable ID being
  treated as authorization.
