# 07 — Flutter / Kotlin Implementation Design

**Scope:** Client-side design for Option C. This is a design, not an implementation. No Dart or Kotlin file is modified in this phase. Interface names are proposals.

---

## 1. Design principles

1. **The Child never self-recovers.** A new installation ID is not a trigger; only a Parent-issued challenge enables rotation.
2. **No secret leaves the device** except as the existing `secret_hash` to the completion endpoint, over TLS.
3. **No new credential is generated by the recovery flow.** The device's existing new secret (created lazily by `SecureStore`) is the one registered. Recovery only makes the server accept it.
4. **Preserve the existing device row.** `serverDeviceId` remains the same; only the server's `secret_hash`/`installation_id` change.
5. **Recovery state is explicit**, never inferred silently.

---

## 2. New client-visible states

Add a derived **credential state** to the Child shell (not a new server field):

| State | Meaning | Detection |
|---|---|---|
| `unknown` | Not yet checked | Startup |
| `confirmed` | Server accepted the current credential (last heartbeat/poll succeeded) | Background sync status / a successful device-authenticated call |
| `unconfirmed` | An active server device exists for this child, but the local credential has never been confirmed in this install | Active device row + no successful device-auth call since install |
| `approvalRequired` | Parent approval is needed; a challenge may be pending | Child has asked and server reports a pending challenge, or Parent has issued one |
| `revoked` | Server row is revoked | `fetchMyDevice()` returns null **and** membership is still active, or an explicit `403 device_revoked` |

**Important:** `unconfirmed` must **not** automatically start recovery. It only changes the UI and offers "Ask a guardian to approve this phone".

A practical detection without new backend state:
- On shell load, `fetchMyDevice()` returns an active row (existing behavior).
- Attempt one cheap device-authenticated call (or wait for the first heartbeat) and observe 401.
- Persist a non-secret local flag `credential_unconfirmed` in `SecureStore` after a 401 from a device-authenticated call, and clear it on a successful heartbeat. This avoids a server probe and never stores secrets.

`GuardianService` already records `guardian_lastError`; extend it to classify `DeviceHttpException.statusCode == 401` as `credential_unconfirmed` (a stable enum), while keeping the human text.

## 3. Parent flow (Flutter)

### 3.1 Entry point
`lib/features/devices/device_detail_page.dart`, in the existing "Lost or reinstalled phone" section (currently around lines 159-184). Add a **second** action separate from the destructive `Start device recovery`:

- Primary: **"Approve this phone's new credential"** (relationship-preserving).
- Secondary (unchanged, destructive): **"Start device recovery (unlink & re-pair)"**.

The destructive action stays visually and textually distinct; no behavior change to it.

### 3.2 Confirmation dialog
Reuse `_confirmRecovery` style (`device_detail_page.dart:469-483`). Show:
- device display name, platform, `last_seen` age, `status`;
- a warning that the old install will stop reporting;
- explicit confirmation ("Approve credential replacement").

The dialog must identify the **exact device id** (server row) so a Parent with multiple rows (including the E2E-002 revoked row) cannot pick the wrong one. Revoked rows must not offer this action.

### 3.3 Request + challenge display
Call a new repository method, e.g. `requestDeviceCredentialRecovery(deviceId)`, which invokes the new backend action.

Response handling:
- success → show a short-lived one-time code and expiry, with copy/share; explain the Child must enter it on the reinstalled phone;
- `403` → "You do not have permission for this device";
- `409 device_not_active` / `revoked` → "This device is not active; use recovery/re-link";
- `429` → retry-after message using the existing `AppException` mapping;
- `404` → device not found.

No polling of the challenge is required if the Parent reads the code to the Child. Optional realtime status is an owner decision.

### 3.4 Controller changes
`DeviceDetailController`:
- add `isRequestingRecoveryChallenge`, `recoveryChallenge` (code, expiresAt), `recoveryChallengeError`;
- add `Future<bool> requestCredentialRecovery()`;
- do **not** treat a request as success until the server returns a challenge;
- refresh the device row after the Child completes (existing `load()`), and show "Waiting for the phone to reconnect" until `last_seen_at` advances.

### 3.5 Device model
`Device` (`lib/data/models/device.dart`) already exposes `id`, `displayName`, `platform`, `status`, `lastSeenAt`. No model change is required for the Parent. A presentation helper may show "Credential replacement pending".

## 4. Child flow (Flutter)

### 4.1 Where the Child sees the problem
`lib/features/child/child_shell_controller.dart` and `child_home_tab.dart`:
- Add a banner/card: "This phone needs guardian approval to reconnect."
- Provide an input for the one-time code (or scan a QR if the Parent UI includes one).
- Explain that the family link and data are preserved.

### 4.2 Completion sequence
1. Child enters the code.
2. `ChildShellController.completeCredentialRecovery(code)`:
   - read native identity (`getIdentity()`) → `installationId`, `secret`, `secretHash`;
   - call new repository method `completeDeviceCredentialRecovery(deviceId, installationId, secretHash, displayName, ...)`;
   - on success: `session.setDeviceIdentity(identity.copyWith(serverDeviceId: device.id))`, re-run `_ensureIdentityAndSync(device, family)` so `SyncConfig` is written with the same device id + **new** secret (it already is, but re-running guarantees consistency), then `load()`;
   - on failure: map `410 challenge_expired`, `409 recovery_already_used`, `403 forbidden`, `429 rate_limited`, `400 validation` to actionable messages.
3. Never display the secret or hash.

### 4.3 The "ask a guardian" path (optional UX)
If the owner wants a Child-initiated request:
- Child calls `requestDeviceCredentialRecovery` with its own `device_id` (server still requires an **active parent** to approve; the Child's call only creates a **pending request**, not a challenge).
- Parent sees it in device detail / requests tab and must explicitly approve, which then issues the code.
- This is a better UX but adds a second authorization state. Recorded as owner decision; the minimum design is Parent-initiated only.

### 4.4 Child enrollment controller
`ChildEnrollmentController.registerDevice()` currently returns "already registered" when `device.value != null` (`child_enrollment_controller.dart:264-279`). Do **not** change it to auto-recover. Change only the message/behavior to offer the recovery screen when the shell has flagged `credential_unconfirmed`. A Child who is genuinely unlinked still follows the existing pairing flow.

## 5. Repository and service changes (Flutter)

`lib/data/repositories/repository_contracts.dart` `DeviceRepository` — add (proposed names):

| Method | Caller | Backend |
|---|---|---|
| `requestCredentialRecovery(deviceId)` → challenge metadata | Parent | `family-admin` new action or new function |
| `completeCredentialRecovery({deviceId, installationId, secretHash, displayName, ...})` → `Device` | Child | `device-register` new action `recovery_complete` |
| optional `fetchRecoveryChallenge(deviceId)` | Parent | read-only status, optional |

`SupabaseDeviceRepository` implementation uses `EdgeApi.invokeMap` with the existing envelope. The completion call is a **user-JWT** call (not device-authenticated), because the device credential is exactly what is being replaced.

`AppException` mapping already covers 400/401/403/404/409/410/429 (`edge_api.dart:100-146`). New codes (`challenge_expired`, `recovery_already_used`, `device_not_active`) should map to existing categories with specific messages.

## 6. Kotlin / native design

### 6.1 Required
**None for the core rotation.** The new secret is already created and persisted by `SecureStore.deviceSecret()`; `NativeBridge.getDeviceIdentity()` already exposes `installationId`, `secret`, `secretHash` (`NativeBridge.kt:206-219`); `configureBackgroundSync` already accepts a device id + secret (`NativeBridge.kt:357-379`).

### 6.2 Recommended (small, optional)
1. **Credential-state classification in `GuardianService`**: when `DeviceHttpException.statusCode == 401`, set a stable non-secret flag/`lastErrorCode = "credential_invalid"` instead of only free text (`GuardianService.kt:497-521, 682-690`). This lets Flutter show the recovery card without parsing English text.
2. **Explicit resync after completion**: expose a method to rewrite `SyncConfig` with the same `deviceId` and the (already new) secret, then wake the service (`startForeground` intent), so the Parent sees Online within one heartbeat instead of waiting for the next poll/backoff.
3. **No secret logging**: keep the existing rule; do not add the code/secret to `lastError`.

### 6.3 Must not change
- `SecureStore.installationId()` / `deviceSecret()` generation semantics. Recovery must not regenerate them.
- `DeviceHttpClient` header contract (`x-device-id`, `x-device-secret`).
- `requireDevice` semantics on the server (rotation is a data change, not an auth weakening).

## 7. Compatibility with older installed versions

| Client | Behaviour after server feature ships |
|---|---|
| Old Child build, matching credential | Unaffected; all existing actions unchanged |
| Old Child build, mismatched credential | Still 401 and generic error; cannot complete recovery until updated. Parent can fall back to destructive recovery (Gate E/F). |
| New Child build, old server | Calls unknown action → `unknown_action`; UI shows "Update required"; no damage |
| Old Parent build | No new button; existing destructive recovery unchanged |
| New Parent build, old server | Request fails cleanly with `unknown_action`/404; no partial state |
| Mixed Parent new / Child old | Parent can issue a challenge; Child cannot complete it; challenge expires. The Parent UI must say "the phone must be updated" if completion does not occur before expiry. |

**Server additions are additive**; no existing endpoint changes its contract.

---

## 8. UX acceptance criteria

- The Parent always sees the **target device name and id-derived context** before approving.
- The Child always sees **why** it must act and that the family/data are preserved.
- No screen claims success until `last_seen_at` advances or the completion endpoint returns the same device row.
- The destructive recovery remains available but clearly labelled as "removes the family link and requires re-pairing".
- A failed/expired challenge never traps the user: a new challenge can be issued.
