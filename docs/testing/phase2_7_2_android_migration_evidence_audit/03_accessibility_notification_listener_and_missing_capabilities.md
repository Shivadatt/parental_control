## 1. Executive Purpose & Scope

In early design discussions and legacy roadmap iterations of HAVEN Parent Control, two native Android services were discussed as potential mechanisms for child device enforcement:
1. **`HavenAccessibilityService`**: An Android Accessibility Service intended to monitor active foreground window changes, detect restricted applications, and inject programmatic overlays or home-screen redirects.
2. **`HavenNotificationListenerService`**: An Android Notification Listener Service intended to intercept, inspect, and filter incoming push notifications sent to child devices from social media or messaging platforms.

Furthermore, several previous audit iterations grouped these capabilities into broad permission testing discussions under Owner Decision Gate `P25-OWNER-05`.

This audit performs an exhaustive source-code, AST, manifest, and XML search to determine the exact factual status of these two services and establishes critical governance boundaries regarding what an owner decision can and cannot authorize.

## 3. Epistemological Disambiguation: Permission to Test vs Code Implementation

A serious governance error would occur if the Project Owner were asked to "authorize testing the Accessibility Service" when no Accessibility Service exists in the codebase.

The following strict distinctions are permanently established for HAVEN Parent Control:

```
+--------------------------------------------------------------------------------------------------+
|                            GOVERNANCE DISTINCTION REGISTER                                       |
+--------------------------------------------------------------------------------------------------+
| 1. Owner Authorization to Test an Existing Feature:                                              |
|    • Grants permission to testers to activate a permission or trigger an existing code path      |
|      (e.g., granting CAMERA or RECORD_AUDIO to test active WebRTC calls).                         |
+--------------------------------------------------------------------------------------------------+
| 2. Owner Authorization to Implement a New Feature:                                               |
|    • A software engineering decision authorizing developers to write new classes, modify the     |
|      manifest, and author new native services. (NOT PART OF PHASE 2 OR PHASE 3 TESTING).         |
+--------------------------------------------------------------------------------------------------+
| 3. Source Code Implementation Status:                                                            |
|    • Physical presence of Kotlin, Java, or Dart code in the git repository.                      |
|    • For Accessibility (M08) and Notification Listener (M09): ZERO CODE EXISTS.                  |
+--------------------------------------------------------------------------------------------------+
| 4. Runtime Service Activation:                                                                   |
|    • The operational state of a service running on an Android handset.                           |
|    • A service that is not implemented cannot be activated, tested, passed, or failed.          |
+--------------------------------------------------------------------------------------------------+
```

> [!IMPORTANT]
> **GOVERNANCE PRINCIPLE**  
> An Owner Decision authorizing Android permissions **DOES NOT CREATE MISSING APPLICATION CODE**.  
> The Owner cannot authorize testing non-existent services. Neither `HavenAccessibilityService` nor `HavenNotificationListenerService` can be tested during Phase 3 manual testing under the approved 92-functionality baseline.
