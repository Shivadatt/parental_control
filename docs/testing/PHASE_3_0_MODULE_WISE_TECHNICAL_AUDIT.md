## MODULE A — APPLICATION FOUNDATION

### 1. Architecture & Execution Flow
- **Startup Sequence:** `main()` in `lib/main.dart` initializes Flutter widget bindings, loads `Env` config, creates process-wide `GetxService` instances via `RepositoryBinding` (`SupabaseService`, `LocalSettingsService`, `SessionService`, `DeviceAdminService`, `ConnectivityService`, `EdgeApi`), and mounts `ParentControlApp` in `lib/app/app.dart`.
- **Cached Engine Host:** Android `MainActivity.kt` uses `FlutterEngineCache` (`ENGINE_ID = "parentcontrol_main_engine"`). Swiping away the task or configuration recreation detaches the UI without killing ongoing background capture tracks or WebRTC instances.
- **Routing & Navigation:** `AppPages.routes` (24 named routes) managed by GetX (`GetPage`). Splash controller (`SplashController`) handles the initial state machine:
  1. If backend unconfigured -> `/configuration`.
  2. If local role choice unset -> `/role-selection`.
  3. If no active session -> `/auth/login`.
  4. If email unconfirmed -> `/auth/verify-email`.
  5. If role is parent -> `/parent`.
  6. If role is child -> `/child`.
- **Theme & Appearance:** `AppTheme` supports Light and Dark Material 3 modes (`ColorScheme.fromSeed(seedColor: Color(0xFF2563EB))`). Saved locally in `LocalSettingsService` via `SharedPreferences`.

### 2. Audit Findings
- **Verified:** Cold launch, deep-link parsing (`parentcontrol://auth-callback`), route transitions, and theme toggling verified live on Realme RMX2161 and Pixel 9a emulator.
- **Limitations:** No global uncaught Dart error boundary to display a user-friendly crash dialog (relies on standard Flutter error widget).

## MODULE B — AUTHENTICATION & IDENTITY

### 1. Architecture & Execution Flow
- **Registration Flow:** Parent or Child role chosen during registration is passed in `auth.signUp` user metadata (`data: {'role': 'parent'/'child'}`). Supabase Auth creates the record and triggers `private.handle_new_user()`, creating the corresponding `public.profiles` row with the specified role.
- **Email Verification:** Auth gating is strictly enforced by `auth_session_flow.dart`. If `emailConfirmedAt == null`, the app routes to `VerifyEmailPage`, polling every 3 seconds (`refreshEmailVerification()`) with exponential backoff and allowing manual email resend.
- **Role Assignment:** If an account was registered without metadata, the `auth-bootstrap` Edge Function provides a one-time `set_role` action that updates `profiles.role` from `unset` to `parent` or `child`.

### 2. Audit Findings
- **Verified:** Both Parent (`ankit@gmail.com`) and Child (`ankit1@gmail.com`) sign-in, session restore, email verification redirection, and sign-out verified live.
- **Missing Features:**
  - **Forgot Password / Password Reset:** Completely missing from `LoginPage` and `SupabaseAuthRepository`. No `resetPasswordForEmail()` or recovery screen exists in the client.
  - **Single Active Session:** Not enforced; multiple concurrent logins with the same account across multiple devices are permitted by Supabase Auth.

## MODULE C — FAMILY MANAGEMENT & PAIRING

### 1. Architecture & Execution Flow
- **Family Creation:** Managed via `auth-bootstrap` Edge Function (`create_family`). Inserts a family into `public.families` with the authenticated parent as `owner_id` and adds an active row in `public.family_members`.
- **Pairing Channels:**
  1. **Canonical Child ID:** Format `PC-XXXXXX` generated by `child_contact_ids` table. Parent sends an `invite` via `pairing` Edge Function; child receives an approval card on `/child/requests`.
  2. **8-Character Pairing Code:** Child generates an ephemeral pairing code (e.g. `ABC12345`) expiring in 15 minutes. Parent redeems it via `redeem` action; child confirms via `respond`.
- **Unlinking:** Parents can invoke `unlink_child` via `pairing/index.ts`. Re-sets membership status to `removed` and revokes linked device tokens.

### 2. Audit Findings
- **Verified:** Family creation, membership querying, Child ID generation (`PC-7K4M2QRX`), pairing code generation, and approval workflow verified live.
- **Limitations:** Multi-family switching exists in `ParentShellController` state, but UI dropdown only presents families where user is an active member.

## MODULE D — DEVICE MANAGEMENT & SECURITY

### 1. Architecture & Execution Flow
- **Device Credential Generation:** Native Kotlin `SecureStore.kt` generates a 32-byte CSPRNG secret and stores it encrypted inside `EncryptedSharedPreferences` backed by `AndroidKeyStore`.
- **Device Authentication:** Requests from the Child device to `device-telemetry` and `device-command` authenticate using custom HTTP headers:
  - `x-device-id`: UUID of enrolled device.
  - `x-device-secret`: Plain secret from Keystore.
  The server computes `sha256(secret)` and checks it against `devices.secret_hash` using constant-time comparison (`constantTimeEqualHex`).
- **Telemetry Reporting:** `GuardianService.kt` periodically collects battery level, charging status, and permission grants, invoking `device-telemetry` (`heartbeat`).

### 2. Audit Findings
- **Verified:** Keystore persistence, installation ID generation, battery reporting, and telemetry verified live on Realme RMX2161.
- **Defect E-16 Note:** Reinstalling the debug APK regenerates the local Keystore secret on the device. Because the remote backend retains the previous `secret_hash`, the reinstalled app experiences a 401 until `request_device_recovery` is executed.

## MODULE G & H — SCREEN TIME & APP RESTRICTIONS

### 1. Architecture & Execution Flow
- **Policy Creation:** Parent configures daily quota (minutes), bedtime start/end times, and package allowlist/blocklist on `/parent/screen-time` and `/parent/app-restrictions`.
- **Policy Deployment:** Calls `device-policy` Edge Function (`update`). Generates a new incremental `version` row in `device_policies` and creates an `apply_policy` command in `device_commands`.
- **Child Enforcement:** Child's `GuardianService` polls `device-command`, receives `apply_policy`, and passes it to `PolicyApplier.kt`.
- **Hard Enforcement vs Advisory Mode:**
  - If device is **Device Owner**: `PolicyApplier` invokes `DevicePolicyManager.setPackagesSuspended()`, physically blocking package execution on Android.
  - If device is **NOT Device Owner**: `PolicyApplier` honestly returns `appliedCount = 0, supported = false`, and records an advisory acknowledgement to the server.

### 2. Audit Findings
- **Verified:** Policy versioning, command queueing, and honest advisory acknowledgement verified across Pixel 9a (Parent) and Realme RMX2161 (Child).
- **Limitation:** Physical package suspension requires initial provisioning via Android Enterprise ADB (`dpm set-device-owner`); standard user installs cannot suspend packages.

## MODULE I — REMOTE ASSISTANCE (ONE-WAY AUDIO)

### 1. Architecture & Execution Flow
- **Session Request:** Parent requests assistance via `/parent/assistance`. `remote-session` Edge Function (`request`) creates a pending row in `remote_sessions` and triggers abandoned-session cleanup.
- **Child Explicit Consent:** Child app displays `MediaSelfTestSheet`. Session proceeds ONLY after child manually taps "Allow Assistance".
- **One-Way Audio Stream:**
  - Child initializes WebRTC audio track (`RECORD_AUDIO`) and publishes RTP stream.
  - Parent initializes receive-only peer connection (`offerToReceiveAudio: true`).
  - Audio Assistance runs inside `AudioAssistanceService.kt` with a persistent notification and wake lock.
- **Signaling:** WebRTC SDP offers, answers, and ICE candidates are exchanged via PostgreSQL `webrtc_signals` table over Supabase Realtime channels.

### 2. Audit Findings
- **Verified:** STUN/TURN credential fetching, explicit consent gating, state machine transition guards, and foreground microphone service verified.
- **Privacy Compliance:** Camera is never activated. Parent microphone is never captured or transmitted.

## MODULE O, P, Q — BACKEND, NETWORK & SECURITY

### 1. Database & Security Summary
- **Schema:** 19 relational tables, 14+ stored procedures/RPCs, strict RLS on every table.
- **Service Role Isolation:** Client never receives `SUPABASE_SERVICE_ROLE_KEY`. Administrative operations are mediated exclusively through Edge Functions.
- **Device Credential Isolation:** `secret_hash` is write-only / service-role read-only.
- **API Envelope:** Uniform `{ok, data}` / `{ok, error}` format across all Edge Functions.
