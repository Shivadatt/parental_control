## 2. End-to-End Assistance Flow (Section J)

### 2.1 Request Creation Pipeline
- **Edge Function Naming Note:** In the codebase and hosted deployment, the relevant Edge Function is named **`remote-session`** (not `remote-assistance`).
- **Parent Action:**
  1. The parent navigates to the child device manage screen and taps **"Request audio"** (`lib/features/remote_assistance/remote_assistance_page.dart:184-194`).
  2. The parent controller `RemoteAssistanceController.requestSession()` calls `SupabaseRemoteSessionRepository.request(deviceId: deviceId, kind: SessionKind.audio)`.
  3. This invokes the `remote-session` Edge Function with action `request`.
  4. The Edge Function calls the PostgreSQL RPC `public.request_remote_session(p_device_id, p_parent_user_id, p_kind)`.
  5. The RPC executes atomic checks inside a transaction protected by a per-device advisory lock (`pg_advisory_xact_lock`):
     - Verifies device is active and linked to the requesting parent.
     - Sweeps stale `requested` rows that exceeded their 10-minute expiry.
     - Enforces the concurrency constraint: if any `requested`, `accepted`, or `active` session already exists for that device, it raises `session_in_progress` (SQL state `P0001`).
     - Inserts a new row into `public.remote_sessions` with `status = 'requested'`, `requested_at = now()`, and `expires_at = now() + interval '10 minutes'`.
  6. The Edge Function writes an audit entry:
     `eventType: 'session_requested'` (displayed in UI as `"Assistance requested"`).

### 3.2 Realtime Subscription & Replay Architecture
- Signaling uses Supabase Realtime Postgres Changes:
  - Channel name: `'webrtc-signals:<sessionId>:<timestamp>'` (`private: true`).
  - Event: `PostgresChangeEvent.insert`, table: `'webrtc_signals'`, filter: `session_id=eq.<sessionId>`.
- **The Replay Mechanism (`_replaySignals`):**
  Because Supabase Realtime only broadcasts inserts that occur *after* the client websocket subscription is established, late joiners could miss earlier offers or candidates.
  `SupabaseRemoteSessionRepository._replaySignals()` executes a direct SQL SELECT query on `webrtc_signals` ordered by `sequence ASC` upon subscription establishment to replay any pre-existing signals.
- **Sole-Offerer Negotiation Pattern:**
  - **The parent is always the offerer.** In `RemoteSessionController.join()`, the parent creates the initial WebRTC offer with constraints:
    `{'OfferToReceiveAudio': true, 'OfferToReceiveVideo': latest.kind == SessionKind.video}`.
  - The child receives the offer and responds with `_answerOffer()`.
  - If the child joins before the parent's offer arrives, the child emits an SDP-less ready marker:
    `_remoteSessionRepository.sendSignal(kind: SignalKind.offer, payload: {'ready': true})`.
  - When the parent receives this marker (`_handleChildReady`), it initiates negotiation immediately.

## 4. Deep-Dive: Defect E-2 ("WebRTC Media Never Opens")

### 4.1 Forensic Analysis of "Media: No media is open"
A critical question investigated is why every audited session in the parent session list shows:
`Media: No media is open` (`_J03.txt`, `parent/J10_ra_fresh.png`).

1. **Exact Code Origin:**
   The string is generated by exactly one getter in the entire codebase: `RemoteSession.mediaNote` at [remote_session.dart#L156-L171](file:///d:/parentcontrol_app/lib/data/models/remote_session.dart#L156-L171):
   ```dart
   String get mediaNote {
     switch (status) {
       case RemoteSessionStatus.requested:
         return 'Off — waiting for the child to accept';
       case RemoteSessionStatus.accepted:
         return 'Off — waiting for the child to join';
       case RemoteSessionStatus.active:
         return 'Started by the child; not verified here';
       case RemoteSessionStatus.declined:
       case RemoteSessionStatus.expired:
       case RemoteSessionStatus.failed:
         return 'No media was opened';
       case RemoteSessionStatus.ended:
         return 'No media is open';
     }
   }
   ```
2. **Semantics:**
   `RemoteSession.mediaNote` does **not** inspect `RTCPeerConnection`, does not check ICE status, and receives zero telemetry. It is a static, pure mapping from the server row's `status` column.
   - When a session has been concluded and `status == 'ended'`, it **always** displays `"No media is open"`.
   - Even a hypothetical session that maintained crystal-clear audio communication for an hour will display `"No media is open"` once the parent taps End Session.
   - Therefore, the string `"No media is open"` is a **session termination status**, not empirical proof of media failure.

### 4.2 The Real Media Failure: Missing TURN & NAT Traversal Breakdown
While the UI string itself is a status convention, **live WebRTC audio media actually failed to connect** during testing. Here is the decisive technical breakdown:

#### A. Service Architecture Clarification
The audit brief asks to inspect `lib/data/services/webrtc_service.dart`.
- Forensic fact: **`lib/data/services/webrtc_service.dart` does not exist.**
- WebRTC peer connections are created, managed, and monitored directly inside:
  - `lib/features/remote_assistance/remote_session_controller.dart` (UI controller & WebRTC state machine)
  - `lib/data/repositories/supabase_remote_session_repository.dart` (signaling & ICE fetch)
  - `lib/data/models/remote_session.dart` (ICE config data models)

#### B. ICE / TURN Configuration Pipeline
1. When joining a session, the client requests ICE configuration via `_remoteSessionRepository.fetchIceConfig(sessionId)` -> `remote-session` Edge Function action `ice`.
2. The Edge Function runs `buildIceConfig(readTurnEnv(), userId)` (`supabase/functions/_shared/turn.ts:71-106`).
3. `turn.ts` reads the environment variables:
   - `STUN_URL` (defaults to `stun:stun.l.google.com:19302`)
   - `TURN_URL`
   - `TURN_SECRET`
   - `TURN_TTL_SECONDS` (defaults to 600 s)
4. If `TURN_URL` or `TURN_SECRET` is missing, `turn.ts` returns:
   ```json
   {
     "ice_servers": [{ "urls": ["stun:stun.l.google.com:19302"] }],
     "turn_configured": false,
     "warning": "TURN is not configured. Audio and video may fail on restrictive networks."
   }
   ```

#### C. Hosted Project Reality (Evidence-Based)
As established in `docs/supabase-hosted-state-verification-2026-11-05.md` §7, the hosted Supabase project `hhqgreaoqulmfwfwarhc` has the following secrets inventory:
- Present: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `STUN_URL`, `CRON_SECRET`, `PAIRING_HASH_PEPPER`.
- **Absent:** `TURN_URL`, `TURN_SECRET`.
- Consequence: Every single ICE configuration issued to both the parent emulator and the child physical phone was **STUN-only**.
- Runtime Proof from Evidence:
  The child session screen in the audit literally displays the yellow banner ([_J16.txt](file:///d:/parentcontrol_app/docs/testing/final_two_device_audit/child/_J16.txt)):
  `"Relay not configured | No TURN relay is configured. Audio/video may fail to connect on networks with strict firewalls or carrier NAT."`

#### D. NAT Traversal Failure Mechanism
WebRTC connectivity depends on Interactive Connectivity Establishment (ICE, RFC 8445):
1. **Candidate Gathering:**
   - With STUN-only, peers gather only **host candidates** (local IP addresses) and **srflx candidates** (server-reflexive public IP/port discovered via STUN).
   - Zero **relay candidates** (`typ relay`) are generated because no TURN server is configured.
2. **Endpoint Topologies:**
   - **Parent Endpoint:** Android Emulator (`emulator-5554`) running on Windows host. The emulator operates in an isolated private network with IP `10.0.2.15`, behind Android emulator virtual NAT (QEMU user-mode networking). Host candidates gathered by parent are `10.0.2.x`.
   - **Child Endpoint:** Physical realme RMX2161 (`5HXWRGQ4IFU8WS4T`) connected via cellular data or residential Wi-Fi behind Carrier Grade NAT (CGNAT) / symmetric NAT.
3. **Connectivity Check Failure:**
   - Symmetric NAT / CGNAT allocates different external port mappings for different destinations. The STUN server sees one port mapping, but peer-to-peer STUN binding requests from the emulator to that port are dropped by the child's carrier firewall.
   - Similarly, the emulator's virtual NAT drops inbound UDP packets from the child phone because no external port forwarding exists on the Windows host.
   - Peer connection state transitions:
     `RTCPeerConnectionState.RTCPeerConnectionStateNew`  
     -> `RTCPeerConnectionState.RTCPeerConnectionStateConnecting`  
     -> `RTCPeerConnectionState.RTCPeerConnectionStateFailed`.
   - The ICE connection state transitions to `RTCIceConnectionStateFailed`.
   - In `RemoteSessionController._handlePeerConnectionState`, state `Failed` triggers `_onMediaFailed()` and attempts ICE restart backoff (`_scheduleIceRecovery()`), which repeats until recovery is exhausted because no routable candidate pair can ever be formed.
   - Audio RTP flow is monitored by `_sampleMediaStats()` polling `inbound-rtp` packets. Because no packets are received, `isMediaFlowing` remains `false`.
   - The parent UI chip never transitions to green `"Active"` (which requires `hasActivePeer.value && isConnected.value && isMediaFlowing.value`), remaining at `"Connecting"`, `"Checking audio…"`, or displaying `"Media connection failed"`.

### 4.3 Parent Receive-Only Policy Verification
Code inspection confirms strict adherence to privacy and security architecture:
1. **Microphone Access:**
   In `RemoteSessionController._createPeer` and `_requestMediaPermissions`:
   `if (!isChildRole) return false;`  
   The parent device **never** requests `RECORD_AUDIO` permission.
2. **Audio Track Generation:**
   In `RemoteSessionController.join()`:
   ```dart
   if (localStream != null) {
     for (final track in localStream.getTracks()) {
       await peerConnection.addTrack(track, localStream);
     }
   }
   ```
   For the parent role, `localStream` is `null` (only the child executes `_captureUserMedia`).
   The parent creates the SDP offer with receive-only directives:
   ```dart

   'OfferToReceiveVideo': latest.kind == SessionKind.video
   ```
3. **Audio Output:**
   When the child's remote track arrives on the parent, `peerConnection.onTrack` invokes `_attachRemote(stream)`, which calls `Helper.setSpeakerphoneOn(true)` to route incoming audio to the loudspeaker.

## 5. Session Cleanup & Stranded Sessions (Defect E-12)

### 5.1 Expiry Mechanics: Pending vs Consented Sessions
The codebase implements a strict architectural distinction regarding session lifetime:
- **Pending Requests:** Carries a hard 10-minute deadline (`expires_at = requested_at + 10m`). If the child does not accept within 10 minutes, the request expires and cannot be accepted.
- **Consented Sessions:** Under the parent-controlled lifetime architecture (migration `20261028000200_parent_controlled_session_lifetime.sql`), `expires_at` is set to `NULL` upon consent. The session is owned by the parent and does not expire on a timer; it stays alive until the parent explicitly ends it.

### 5.2 Hosted Divergence & The Stranded Session Blocker
In the live hosted environment, several factors compound into Defect E-12:

1. **Undeployed Edge Function Rework:**
   - The hosted `remote-session` Edge Function is **v5**, deployed on **2026-10-26T16:24Z**.
   - The parent-controlled lifetime code was authored on **2026-10-28**.
   - No Edge Functions were redeployed after 2026-10-27.
   - Consequently, the deployed Edge Function still executes the old behavior: it stamps a 30-minute `expires_at` on consent, and its `ice` action rejects calls if `expires_at` is past or missing.
2. **Unapplied Abandoned Sweep Migration:**
   - Migration `20261030000100_abandoned_session_sweep.sql` (which defines `public.expire_abandoned_sessions()` and index `remote_sessions_abandoned_idx`) is **NOT applied** on the hosted Supabase database (`docs/supabase-hosted-state-verification-2026-11-05.md` §5 & §9).
   - Furthermore, `pg_cron` is not installed, so no background database worker sweeps stale sessions.
3. **What Happens on Unclean Disconnect:**
   - If a parent or child closes the app, loses internet connection, or crashes without the parent tapping "End Session" (which calls Edge Function action `end`), the database row remains in `status = 'accepted'` or `status = 'active'`.
   - Native device commands cannot clear it: `GuardianService.kt:456-460` deliberately refuses `end_session` background commands with:
     `"Session media is managed by the visible assistance screen and cannot be ended by the background service."`
   - When the parent later attempts to start a new assistance session:
     `public.request_remote_session()` takes an advisory transaction lock and queries:
     ```sql
     if exists (
       select 1 from public.remote_sessions
       where device_id = p_device_id
         and status in ('requested', 'accepted', 'active')
     ) then
       raise exception 'session_in_progress' using errcode = 'P0001';
     end if;
     ```
   - Because the stranded row is in `accepted` or `active` status (and stale sweep only cleans `requested` rows), the function throws `session_in_progress`.
   - The parent app receives HTTP 409 / error code `session_in_progress`, **permanently blocking all future assistance requests for that child device** until the row is manually updated or terminated.

## 7. Actionable Remediation Blueprint

To resolve Defect E-2 (media connectivity) and Defect E-12 (stranded sessions) in production, execute the following three remediation tracks:

### Track 1: Provision Coturn Relay & Configure Supabase Secrets (Fixes E-2)
1. Deploy a standard `coturn` server on a public cloud VM (e.g. Ubuntu LTS on AWS/GCP/DigitalOcean) with public static IP.
2. Configure coturn with long-term credential mechanism (`use-auth-secret`) and static HMAC secret (`static-auth-secret`).
3. Set the required Edge Function secrets in the Supabase Dashboard (`Project Settings -> Edge Functions -> Secrets`):
   ```bash
   TURN_URL="turn:turn.yourdomain.com:3478?transport=udp,turn:turn.yourdomain.com:3478?transport=tcp"
   TURN_SECRET="<your-generated-32-byte-hex-secret>"
   TURN_TTL_SECONDS="3600"
   ```
4. Verify via `remote-session` action `ice` that response includes `turn_configured: true` with ephemeral credentials. Both peers will then gather `typ relay` candidates, allowing ICE to connect through carrier CGNAT and emulator NAT.

### Track 2: Apply Database Sweep Migration & Deploy Edge Functions (Fixes E-12)
1. Apply unapplied migration `supabase/migrations/20261030000100_abandoned_session_sweep.sql` to create `public.expire_abandoned_sessions()` and the `remote_sessions_abandoned_idx` index.
2. Deploy the latest version of Edge Function `remote-session`:
   ```bash
   supabase functions deploy remote-session
   ```
   This ensures the deployed function incorporates the parent-controlled session lifetime logic, abandoned session sweep, and correct `ice` action authorization.
3. Configure an external cron monitor or pg_cron to periodically call `public.expire_abandoned_sessions()` to ensure abandoned sessions do not strand active device slots.

### Track 3: Diagnostic UI Refinements
1. In `lib/data/models/remote_session.dart`, update `RemoteSession.mediaNote` for terminal states to explicitly distinguish normal teardown from never-connected sessions, for example:
   - If session ended with 0 audio packets exchanged: `"Session closed (no audio was transmitted)"`.
   - If session ended after active transmission: `"Session closed (audio was active)"`.
2. This will prevent confusion between normal session teardown and connectivity defects.
