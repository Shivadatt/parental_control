## 1. The Three-Dimensional Orthogonal Dependency Framework

To eliminate conflation between database requirements, infrastructure environment readiness, and native mobile operating system privileges, every manual test case in HAVEN Parent Control is independently classified across three orthogonal dimensions:

```
+----------------------------------------------------------------------------------------------------+
|                                THREE INDEPENDENT DEPENDENCY DIMENSIONS                             |
+----------------------------------------------------------------------------------------------------+
| Dimension 1: Database Migration Dependency (M-Class)                                               |
| • M0: No database or migration dependency (client-only / offline / mock)                          |
| • M1: Existing compatible schema required (read/write against operational schema)                 |
| • M2: Static migration inspection required (source SQL review only)                                |
| • M3: Fresh database / clean migration replay required (unpolluted multi-tenant baseline)         |
| • M4: Runtime schema verification required (RPCs, triggers, cascade purges)                        |
+----------------------------------------------------------------------------------------------------+
| Dimension 2: Environment Readiness (E-Class)                                                       |
| • E0: No backend environment required (completely local / disconnected)                            |
| • E1: Existing compatible backend required (shared QA backend with operational tables)            |
| • E2: Isolated backend / tenant required (dedicated family quarantine fixture)                     |
| • E3: Fresh infrastructure and schema provisioning required (clean project / Docker spin-up)       |
| • E4: Specialist hardware or platform environment required (sensors, audio loopback, ADB host)    |
| • E5: Combined environment requirement (e.g. isolated backend + dedicated test handset)             |
+----------------------------------------------------------------------------------------------------+
| Dimension 3: Android Native Capability Dependency (A-Class)                                        |
| • A0: No special Android privilege (standard Flutter UI / lifecycle)                              |
| • A1: Ordinary runtime permission (Camera, Mic, Location, Notifications)                          |
| • A2: Special app access (Usage Access via AppOps)                                               |
| • A3: Device Admin (ParentControlDeviceAdminReceiver active)                                      |
| • A4: Device Owner (DevicePolicyManager.setPackagesSuspended - Requires out-of-band ADB setup)      |
| • A5: Accessibility Service (UNAVAILABLE IN CURRENT IMPLEMENTATION - M08)                         |
| • A6: Notification Listener (UNAVAILABLE IN CURRENT IMPLEMENTATION - M09)                         |
| • A7: Specialist hardware or multiple device requirement (pairing scan, dual phones)               |
| • A8: Combined Android capabilities (e.g. Foreground daemon + Location + Notifications + Keystore)|
+----------------------------------------------------------------------------------------------------+
```

## 4. Key Cross-Dimensional Architectural Takeaways

1. **Orthogonality of M0 and Environment Provisioning**:
   - Exactly **26 tests are M0** (No Database Dependency). They run in memory or against local platform APIs.
   - 18 of these 26 are **`M0 + E0`** (completely local / disconnected).
   - 8 of these 26 are **`M0 + E4`** (no backend required, but specialist Android test hardware or sensor loopback required).
   - An M0 test does not become M1 or M3 simply because the application build is configured with a backend URL.

2. **The M1 Operational Baseline**:
   - Exactly **61 tests are M1** (Existing Schema Required). They represent standard functional operations (reading/writing telemetry, policies, devices, family records).
   - 30 of these 61 are **`M1 + E1`** (executable on shared staging/QA without isolation).
   - 30 of these 61 are **`M1 + E2`** (requiring dedicated family tenant quarantine to avoid collisions).
   - 1 is **`M1 + E5`** (`TC-EXP-56` requiring isolated tenant + native daemon).

3. **Android Privilege Segregation**:
   - 71 tests are **`A0`** (standard application code, zero special privileges).
   - Only **1 test (`TC-APP07`) is `A4`** (strictly requiring Device Owner).
   - Accessibility (`A5`) and Notification Listener (`A6`) are **0.0% (UNAVAILABLE)** in the current repository.
