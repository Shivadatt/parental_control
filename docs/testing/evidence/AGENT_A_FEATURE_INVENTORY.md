# AGENT A — Source-grounded feature inventory & parent↔child integration map

Scope: static source audit of `D:\parentcontrol_app` (pubspec `parent_control`,
applicationId `com.parentcontrol.parent_control`). No device command, no git, no
file was modified other than this report. No secret values are reproduced — only
compile-time variable **names**.

Read the code paths, not the docs: `lib/`, `android/app/src/main/kotlin/com/parentcontrol/parent_control/`,
`supabase/functions/`, `supabase/migrations/`, `supabase/config.toml`, `pubspec.yaml`.

Legend for status:
* **REAL** — UI → controller → repository → server/native enforcement all exist in source.
* **PARTIAL** — chain exists but is gated, one-way, or incomplete at one end.
* **MOCK-OR-DEMO** — the screen presents state that no backend/native layer produces.
* **NOT-IMPLEMENTED** — named in models/DB/enum but no producing or consuming code path.

## E. BACKEND CONTRACT

All functions: `POST` only (405 otherwise), body `{action, …}`, envelope `{ok,data}` / `{ok,error}`; OPTIONS preflight (`_shared/cors.ts`). Service-role client is created lazily from server env `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` (`_shared/auth.ts:49-65`).

* **User JWT** — `requireUser` `:80-127` (bearer ≥ 20 chars, `auth.getUser`, loads `profiles`, optional `requireVerifiedEmail`).

A user JWT or a bare device id is never accepted (`:2-3`).

## F. KNOWN TEST-RELEVANT GAPS

**F1. Device Owner is the single biggest functional gate — and the app cannot grant it.**
* App suspension only works as Device Owner. `PolicyApplier.kt:140` emits "Device Owner provisioning is required to suspend apps on this device. No apps were suspended." and reports `desired_count=N, applied_count=0, enforcement_supported=false`.
* `res/xml/device_admin.xml` declares `<uses-policies/>` (no legacy policies), and there is **no DPC/QR/NFC provisioning class and no `android_dpc` module** (searched). The intended step is documented as an adb command in `ParentControlDeviceAdminReceiver.kt:13` (`dpm set-device-owner …`).
* Consequence: on a **device-admin-only** phone, app blocks, block-all-except-allowed and the daily quota all land as `unsupported` (`enforcement.ts:302-308`) — which **deliberately advances `devices.policy_version`** to stop retry loops (`enforcement.ts:366-368,386`). Parent UI surfaces this as the `App suspension is not supported here` banner (`device_detail_page.dart:99`).
* Child-side verification then reports "not verified" rather than claiming enforcement (`child_shell_controller.dart:502-568`, labels `:116-135`).

**F2. Usage Access gates every number.**
`PACKAGE_USAGE_STATS` is user-granted only (comment `AndroidManifest.xml:19-23`); `NativeBridge.getDailyUsage` returns `usage_access_denied`; quota planning requires `UsageReporter.hasAccess` **and** isOwner. Parent shows `No usage numbers available` (`screen_time_page.dart:88`) and `usagePermissionText` (`screen_time_controller.dart:204-211`).

**F3. No push of any kind.** No FCM plugin, no notification service in the manifest, no token table. Child→parent "notifications" are only: (a) Supabase realtime on `safety_alerts` while the parent app is open, and (b) polling. An offline child therefore **cannot** wake a closed parent app.

**F4. Policy delivery is pull-only, and commands are delivered exactly once.**
`device_commands` is in the realtime publication but **no Dart or Kotlin subscriber exists** — delivery is the 20 s poll (`GuardianService.kt:39,360-372`). `poll_device_commands` flips `pending → delivered` and never back (`20260101000100_functions.sql:620-635`); if the ack then fails, the command expires and the policy stays `pending` (`enforcement.ts:311-321`, `last_error='enforcement_counts_missing'|'command_expired'`). There is no device-initiated policy *fetch*: `applyStoredPolicy` re-applies the locally stored JSON (`PolicyApplier.kt:253-275`), so a fresh/cleared install cannot be rescued by `Request device sync` — it answers "No policy has been stored on this device yet."

**F5. Bedtime is cosmetic.** Stored, validated in pairs (`_shared/policy.ts:212-218`), reported as informational `bedtime_active` (`PolicyApplier.kt:502-503`); a bedtime-only policy yields enforcement status `pending` + `limits_enforcement_unverified` (`enforcement.ts:341-351`).

**F6. Two alert types can never fire.** `app_blocked` and `permission_missing` exist in the Dart enum and DB CHECK (`20260101000000_core.sql:302-303`) but have **no INSERT site** — blocking an app produces no parent alert.

**F7. Offline alerts depend on external cron.** See §E. Threshold logic exists (`detect_offline_devices`, 15 min / 6 h dedupe) but nothing in this repo invokes it on a schedule.

**F8. Android 15 kills boot-resume of the guardian service.** `BootReceiver.kt:31-37` records "Android 15 does not allow starting visible background sync at boot. Open Parent Control to resume it." and returns. Also returns early if notifications are not granted (`:38-44`). On a reboiled child phone, **telemetry stops until the child opens the app** — and the parent just sees the device age into Stalled/Offline.

**F9. Guardian service won't start without notification permission.** `child_shell_controller._resumeBackgroundWork` `:617-666` starts guardian only if notifications are granted, then `startLocationTracking(intervalSeconds: 60)`. `Retry background protection` (`child_home_tab.dart:376`, `child_settings_tab.dart:297`) is the recovery affordance.

**F10. Silent degradations that will look like "no data" rather than an error.**
* Parent Location screen has **no auto-refresh** (`location_controller.dart` has no timer) and **no map** — decimal lat/lng only (`location_page.dart:307-313`).
* Parent remote-assistance **list** has no auto-refresh; only the `Refresh` icon (`remote_assistance_page.dart:43`).
* Device detail has no auto-refresh (`device_detail_controller.dart:63-98`); policy evidence requires `Refresh policy state` `:312`.
* `watchFamilySessions` (`supabase_remote_session_repository.dart:209-221`) is implemented but **never called** — the parent session list is not live.
* Usage snapshot is hourly and app snapshot is 30-minute (`GuardianService.kt:42-43`); `apps_upload` also fires right after a successful policy apply (`:411-414`).
* Mock/fused locations are deliberately never uploaded (`GuardianService.kt:596-604`) — a mocked GPS fixture will show as "no location", not as a wrong location.

**F11. Two parent Settings switches are inert.** `Show local notifications` and `Location sharing reminder` write SharedPreferences only (`parent_settings_controller.dart:147-178`); `LocalSettingsService.locationSharingEnabled` has **zero readers** and `notificationsEnabled` is read only to re-render its own switch (`parent_settings_controller.dart:113`). The UI text honestly labels them "local to this phone only" (`settings_body.dart:119-122`), but they produce no behavior — do not test them as features.

**F12. `end_session` command is defined but unused and self-refused.** See A#42. Session teardown reaches the child via realtime `remote_sessions` plus the child's own `session_state` poll (`AudioAssistanceService.kt:737-754`), never via `device_commands`.

**F13. Child "Stop sharing" never closes the server session.** `child_shell_controller.dart:425-441` releases camera/mic and the registry only; the UI says so (`child_session_page.dart:130-131`, `:89-93`). Parent status chips are **server state, not media state** (`remote_assistance_page.dart:92-94,309-312`). Test the parent `End` action, not the child's stop, for session closure.

**F14. One active device per child account.** Second registration → `device_already_registered` 409 (`device-register/index.ts:197-210`); re-registering the same `installation_id` re-credentials instead (`:166-195`). Re-enrolling a revoked device needs parent-initiated recovery.

**F15. Enumeration/rate-limit behavior will bite during repeated testing.** Pairing redemption is rate-limited per parent+identifier (`_shared/rate_limit.ts`, `assertPairingRedeemAllowed`/`assertPairingCodeCreationAllowed`/`assertInviteQuotaAllowed`, `pairing_attempts` table `20260101000000_core.sql:414`), returns the identical `The linking code or Child ID is not valid.` for unknown/expired/foreign IDs (`pairing/index.ts:48,301,339,581,593,608`), and the child has a pending-inbox cap. Expect `rate_limited` after bursts — space out redeem attempts.

**F16. Roles are server-assigned and unverifiable locally.** All 8 client-verified `requireUser(..., { requireVerifiedEmail: true })` call sites reject unverified accounts; `account` deliberately does not (`account/index.ts:564-566`, surfaced to users at `settings_body.dart:74-80`). Local role choice is a hint only (`login_page.dart:76-80`).

**F17. Native `applyPolicy` channel is dead code.** Method exists on both sides (`device_admin_service.dart:87`, `NativeBridge.kt:132`) but **no Dart or test call site exists** (grep for `.applyPolicy(` across `lib/`, `test/`, `integration_test/` → 0 hits). Foreground Flutter never enforces; only `GuardianService` does. Killing the service ⇒ no enforcement until it restarts.

## G. Documentation-vs-code contradictions (report as product bugs, not test flake)

**G1. Child screen contradicts the enforcement engine about screen time.**
`lib/features/child/child_restrictions_page.dart:295-301` states verbatim:
> "Daily screen-time limits and bedtime are not enforced system-wide by this Android build. Only app blocks and their schedules are applied through DevicePolicyManager."

But `android/.../policy/QuotaEvaluator.kt` (actions `none|advisory|suspended|suspend_failed`, reasons `quota_*`, `QuotaEvaluator.kt:40-56`) and `PolicyApplier.quotaPlan` **do** suspend apps to enforce `daily_screen_time_limit_minutes` when Device Owner + Usage Access are present, and `device-command/enforcement.ts:399-459` reports that as `enforced`. The child copy is right about **bedtime** (F5) and wrong about the **daily limit**. Expect: parent says `enforced`, child says it isn't.

**G2. `pending_policy_version` cannot self-heal a device with no stored policy.** `device-telemetry/index.ts:150-154` + `GuardianService.kt:519-522` only accelerate a poll; acceleration is useless if the original `apply_policy` command was already consumed (F4). Parent's honest surface for this is `Time remaining today → Unknown — the device has not reported usage yet` (`screen_time_controller.dart:123,130-131`) and the `Refresh policy state` affordance.

**G3. `device_commands` published for realtime but unsubscribed (F4).** A tester watching Supabase traffic will see the publication and reasonably expect push delivery; there is none.
