# Complete Runtime Test-Case Inventory

**Purpose:** execution inventory derived from the seven-page AirDroid benchmark and the read-only HAVEN mapping.  
**Ordering:** this file was written only after reports 01 and 02 were complete. Its existence is the device-test start signal.  
**Current state:** **112 planned tests; 112 `NOT TESTED`; 0 executed.** No ADB, device interaction, runtime evidence, or application/backend change was performed by the planning agent.  
**Source warning:** all HAVEN mappings are supplementary source pointers, never runtime proof. Exact anchors are in `02_HAVEN_FEATURE_TO_PDF_MAPPING.md`.

## Mandatory execution contract

- Use only the currently installed Parent and Child apps, existing authenticated accounts, family, pairing, device credentials, permissions, server records, and residual QA data. Preserve `QA_Test_Zone_Live` if present.
- Record actual Parent/Child identity, package/version, OS, branch/HEAD, network, permission/service baseline, timezone, and original policy/session/zone state before action. Historical identifiers in the brief are not current evidence.
- Do not use ADB for this agent's work. Runtime executors may use only separately permitted inspection means; never expose credentials, tokens, secrets, private coordinates, notification content, or personal message data in retained evidence.
- Do not sign out, unlink, re-pair, create accounts/devices, delete/purge data, uninstall/reinstall, clear data, force-stop, factory reset, provision Device Owner, grant/revoke permissions, bypass OS prompts/privacy indicators, or alter security/power settings.
- A persistent policy/zone/session/network change requires recorded original state, owner authorization, reversibility assessment, and exact safe restoration. If authorization or safe restoration is unavailable, stop and classify `BLOCKED`. Never automatically clean residual data.
- A screenshot from one device cannot prove a two-device feature. Source presence, a button, saved policy, request/API/database row, command acknowledgement, service process/notification, ICE/DTLS connection, or unit test cannot alone prove runtime behavior.
- Every executed case needs start/end timestamp with timezone, exact actions, Parent and Child evidence paths, app versions, network/permission/service state, expected versus actual, status, and reason. Sanitize retained logs.
- Distinguish main app foreground/background, process existence, foreground-service state, service notification, heartbeat, location freshness, successful upload, Parent-observed result, and network state.
- Do not treat an OEM/Android limitation as a HAVEN defect without evidence that HAVEN mishandled a supported state.

## Shared field definitions

These definitions are part of every row, not omitted fields.

- **BASE preconditions:** `BASE` = existing approved Parent/Child relationship verified; actual identities/versions/OS/network recorded; original relevant state captured; both devices available; no prohibited mutation. If BASE fails, the affected test is `BLOCKED`.
- **PERM-BASE:** `PERM-BASE` = actual Usage Access, Accessibility, Notification Access, precise/background location, camera, microphone, notification, Device Admin/Device Owner, MediaProjection, battery optimization, autostart/OEM restriction, Data Saver/background data, and network states inspected read-only where available. Missing permission is recorded, never granted or revoked.
- **EVIDENCE-BASE:** `EVIDENCE-BASE` = timestamp-correlated sanitized Parent and Child screen evidence showing selected device/app version, exact action/result, network and relevant permission/service state; plus permitted service/log/backend evidence where useful. Media cases additionally need Child capture/service evidence and Parent received-media evidence. No secrets or raw private coordinates.
- **SAFE:** `SAFE` = all mandatory execution-contract restrictions above apply. Policy/zone changes require explicit authorization and exact restoration; destructive cases are not executed.
- **Permissions field:** names the capabilities needed to observe the case. It does not authorize granting them.
- **Testability:** `FEASIBLE—read-only`, `CONDITIONAL—existing state/consent`, `CONDITIONAL—authorized reversible change`, `BLOCKED—prohibited mutation`, or `NO WORKFLOW—confirm source-mapped absence`. These are planning classifications, not result statuses.

## Allowed result statuses

`PASS`, `PARTIAL`, `FAIL`, `BLOCKED`, `NOT TESTED`, `NOT IMPLEMENTED`, `NOT APPLICABLE`.

- `PASS`: complete expected behavior observed at runtime with required two-device evidence.
- `PARTIAL`: some behavior worked but a material path is unverified or failed.
- `FAIL`: observed behavior contradicts expected behavior.
- `BLOCKED`: required device, permission, capability, account, authorization, or safe condition unavailable.
- `NOT TESTED`: not executed.
- `NOT IMPLEMENTED`: feature confirmed absent from HAVEN after the prescribed confirmation; source mapping alone is insufficient.
- `NOT APPLICABLE`: feature does not apply to the current platform/product scope, with reason.
